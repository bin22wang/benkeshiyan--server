## 二、详细说明

### F01: `get_jpeg_b64` 缓存失效返回 None（严重）

**文件**: `server_app/vision.py` — `CameraManager.get_jpeg_b64`

**原因**: `get_jpeg_bytes` 编码成功后会将 `jpeg_b64` 置 None 并更新 `jpeg_ts`。随后 `get_jpeg_b64` 的判断条件仅检查 `jpeg_ts < frame_ts`，由于时间戳已相等，条件为 False，直接返回被置空的 `jpeg_b64`（即 None）。

**修复**: 在 `get_jpeg_b64` 的判断条件中增加 `or st.get('jpeg_b64') is None`，与 `get_jpeg_bytes` 保持对称。

```python
# 修复前
if st.get('jpeg_ts', 0) < frame_ts:
# 修复后
if st.get('jpeg_ts', 0) < frame_ts or st.get('jpeg_b64') is None:
```

---

### F02: 手动绑定锁外访问共享状态竞态（严重）

**文件**: `server_app/routes/vision.py` — `manual_bind_confirm` / `manual_bind_skip`

**原因**: 两个函数在 `with state.vision_lock` 块外通过 `mbs` 引用读取 `mbs["finished"]` 和 `mbs["bound_so_far"]`。若并发请求（如 `manual_bind_cancel`）在此期间重置状态，会读到被篡改的值。

**修复**: 在锁内将所需值拷贝为局部变量（`finished` 布尔值、`bound_so_far_copy` dict 副本、`cameras` list 副本），锁外只使用局部变量。

---

### F03: 非 finished 分支未检查 binder 为 None（严重）

**文件**: `server_app/routes/vision.py` — `manual_bind_confirm` / `manual_bind_skip`

**原因**: `binder = state.vision_state.get("binder")` 可能返回 None，但非 finished 分支直接传入 `_capture_camera_frame`，内部 `binder._open_camera(...)` 会抛 `AttributeError`。对比 `manual_bind_refresh` 有判空检查，三处不一致。

**修复**: 在非 finished 分支的 `_capture_camera_frame` 调用前增加 `if not binder:` 返回 500。在 finished 分支的 binder 为 None 时也清理 `active` 状态。

---

### F04: `manual_bind_start` 异步线程无异常兜底（严重）

**文件**: `server_app/routes/vision.py` — `manual_bind_start._start_task`

**原因**: `_start_task` 无 try/except，若 `binder.list_available_cameras()` 抛异常，`active` 不会被置 True，前端轮询 status 永远得到 `active: False`，流程静默卡死。

**修复**: 包裹 try/except，异常时打印日志并将 `active` 置 False，让前端能感知失败。

---

### F05: MJPEG `switch_to` 与检测循环争锁（高）

**文件**: `server_app/routes/vision.py` — `mjpeg_stream` + `server_app/vision.py` — `CameraManager`

**原因**: 每次 MJPEG 请求都调用 `camera_manager.switch_to`，该函数持有 `_switch_lock`，与 `vision_loop` 的相机切换互斥。多客户端同时请求或 MJPEG 与检测切换同时发生时，会反复争用锁。

**修复**: 在 `CameraManager` 新增 `is_running(index)` 方法（仅获取 `_lock`，不获取 `_switch_lock`）。MJPEG 请求前先检查 `is_running`，已在运行则跳过 `switch_to`，避免不必要的锁竞争。

---

### F06: `make_step_runtime()` 无条件求值浪费（中）

**文件**: `server_app/vision.py` — `mark_waiting_image_started`

**原因**: `setdefault(car_id, make_step_runtime())` 的第二参数会无条件求值，即使 key 已存在也会创建后丢弃。

**修复**: 改为先 `get` 再按需创建：
```python
step_runtime = state.reconstruct_state.setdefault("step_runtime", {})
runtime = step_runtime.get(car_id)
if runtime is None:
    runtime = make_step_runtime()
    step_runtime[car_id] = runtime
```

---

### F07: `maybe_update_snapshot_lowfreq` 节流无锁（中）

**文件**: `server_app/vision.py` + `server_app/state.py`

**原因**: `snapshot_lowfreq_state["last_ts"]` 的读-改-写无锁保护。当前仅 `vision_loop` 单线程调用，但存在潜在竞态风险。

**修复**: 在 `state.py` 新增 `snapshot_lowfreq_lock = threading.Lock()`，在 `maybe_update_snapshot_lowfreq` 中用该锁保护节流判断与时间戳更新。

---

### F08: `np.load` 未关闭文件句柄（中）

**文件**: `Car_vision_system/car_vision_system.py` — `PoseEstimator.load_params_for_car`

**原因**: `data = np.load(params_path)` 返回的 NpzFile 对象未关闭，文件句柄可能未及时释放。

**修复**: 改用上下文管理器 `with np.load(params_path) as data:`，确保文件句柄及时关闭。

---

### F09: `get_vision_image` 直接键访问可能 KeyError（中）

**文件**: `server_app/routes/vision.py` — `get_vision_image`

**原因**: 使用 `state.vision_state["current_image"]` 等直接键访问，若键缺失会抛 KeyError。同文件其他路由均用 `.get()`，此处不一致。

**修复**: 统一改用 `.get()` 方式访问。

---

### F10–F12: 死代码与注释修正（低）

- **F10**: 删除 `vision_loop` 中未使用的 `previous_cam` 变量。
- **F11**: 修正 `update_vision_snapshot` 中"使用编码缓存"的误导注释（`encode_frame` 实为无状态编码）。
- **F12**: 删除 `manual_bind_confirm` 中未使用的 `bound_result` 变量。

## 四、未修改的已知设计约束（保留说明）

以下项经评估后选择保留，不做修改：

1. **`time.sleep(0.3)` USB 冷却等待**: `manual_bind_confirm`/`skip`/`manual_bind` 中的 300ms sleep 是共享 USB 总线切换的必要冷却时间，移除会导致摄像头打开失败。在单线程部署下阻塞可接受。

2. **`_capture_camera_frame` 调用 `binder._open_camera` 私有方法**: 虽然访问了下划线方法，但 `DeviceBinder` 和路由同属一个项目，重构为公开方法需更大范围改动，暂保留。

3. **`PoseEstimator` 中 `from tag_roi_locator import TagRoiLocator` 绝对导入**: 依赖 `sys.path` 包含 `Car_vision_system` 目录，由 `app.py:_init_vision()` 保证。当前架构下正常工作。
